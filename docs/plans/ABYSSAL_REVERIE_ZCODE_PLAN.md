### 3. 跨版本固定约束

1. React → Gateway → Rust → SQLite 保留。所有计时/统计资格由 Rust 判断；前端只显示权威字段和可校正的暂计值。
2. 时间内部用整数毫秒；旧秒数在迁移边界显式乘 1000。分钟和百分比只在显示时取整。
3. 从 v1.2 起，主钟与任务贡献分离；同设备同一瞬间至多一个活动片段。预算、实际投入、完整轮数、任务完成分别表达。
4. 片段先有稳定 ID 再持久化；重复命令以操作 ID 和参数摘要查回执；同一 ID 不同参数拒绝。重复回执不能覆盖更新的运行快照。
5. 请求携带轮次/任务标识和期望 revision；档案由 Rust 当前上下文解析。上下文代际在v1.2恢复/重建时即可使用，v1.4扩展到换号。先验证当前上下文和授权，再查该档案回执，之后校验实体revision；拒绝旧窗口和旧网络回调。
6. 新统计按历史稳定项目/类别 ID 汇总，不按当前任务归属重写历史。历史不能可靠映射时单列未映射桶。
7. 查询采用 `[from,to)`；自然日使用日历零点。v1.2 新片段按有效区间分桶，旧总量按原会话开始日归属并标注局限。
8. 活动列表从后端贡献资格筛选；完整备份包含未达门槛、放弃和休息等原始记录。v1.2 允许“本轮部分放弃但已有确认贡献”，不能再用会话 abandoned 一票过滤已保存时间。
9. 保留单写协调能力；锁内只做短事务，网络、文件传输、大量序列化不长期占计时写锁。不要为了同步引入另一套任意直写连接。
10. 归档不改变完成态；删除不级联删除历史。档案间的对象关联与读取都必须隔离。
11. 关闭窗口不等于退出进程。后台结算、自动休息不依赖前端事件送达；事件丢失后从快照恢复。
12. SQLite `user_version`、备份 `formatVersion`、同步 `protocolVersion` 独立递增。未来格式拒绝写入，迁移失败不触发损坏重建。
13. 不擅自引入树/奖励、项目分组、多对多主层级、远端运行钟接力或强制登录。

### 4. ZCode 执行规则

先读取仓库本地 `AGENTS.md`、`CLAUDE.md`、本索引和当前版本计划。实际仓库中的工具链、脚本和锁文件为准；当前 `AGENTS.md` 仍含 Figma Make 开发服务器假设，不能据此认定 Windows 上已有服务运行。

在仓库根目录执行以下只读检查，确认位置后才开始改动：

```powershell
git status --short
git rev-parse HEAD
git log -5 --oneline
Get-Content package.json
Get-Content src-tauri/Cargo.toml
Get-Content src-tauri/tauri.conf.json
```

基线不同不自动回退；记录差异，按函数重新定位。用户未提交文件保留；需要隔离时创建工作分支/工作树。不要凭本文中的 `D:\Project\...` 示例猜目录。

每个工作包按“复现/定义行为 → 最小修改 → 有效验证 → 更新记录”执行。计时、数据迁移、并发、导入、同步必须有行为测试；静态文案、资产登记等不强制写镜像测试。**不以测试数量作为完成度。** 修正产品语义涉及的旧测试要说明原因，不可删测试逃避失败。

版本门禁（在 Windows 仓库根目录，依赖按锁文件安装）：

```powershell
pnpm install --frozen-lockfile
pnpm verify
cargo test --manifest-path src-tauri/Cargo.toml --locked
pnpm tauri build --no-bundle
```

新引入依赖时有意更新对应锁文件并审查差异，再运行 `--locked`。发布候选另运行 `pnpm tauri build` 并验证 NSIS 与便携 EXE。保留 `custom-protocol`，防止生产包再次依赖开发服务器。对正式发版同步 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json` 和 Cargo.lock 中自身包版本。

文档更新 `docs/CHANGELOG.md`、`docs/ACCEPTANCE_GUIDE.md`、`docs/REGRESSION_REPORT.md`；新建/续写 `docs/plans/EXECUTION_STATUS.md`，记录工作包、实际 commit、命令、退出码、证据位置、未测环境。源码测试通过和 Windows 实机通过分别记载。不能把本计划复制成“已经通过”的回归报告。

每版验收后再进入下一版。合并、打标签和发布服从当前会话授权及仓库规则，不由“计划中提到”推定已获生产发布授权。云厂商区域/预算和真实账号测试是 v1.4 外部门，不阻塞 v1.1.2/v1.2 本地实现。

# PLAN-120

## v1.2.0 类别、项目、任务与可靠计时计划

> 前置：v1.1.2 已验收；遵循 [执行索引](#plan-index)。建议分支 `feature/v1.2-tasks-timer`。
> 状态：待实施。本文的数据/行为契约固定；具体 DTO 与 SQL 在本版开工时根据前版代码落实。
> 本版是主链路最大改动，分工作包逐一验收，不一次重写全部 App/repository。

### 1. 固定需求与取舍

主层级严格为 **类别 → 项目 → 任务**。一个项目属于一个类别，一个任务至多属于一个项目；任务允许独立存在。类别只组织项目，不再给任务多填一套类别。没有项目分组表，也不新增多选标签系统。

旧 `tags`、`task.tagId` 作为迁移来源/兼容数据保留，不继续在新任务表单中与类别平行展示。旧标签的自定义信息保留于迁移审计和历史记录，不悄悄丢弃。

| 业务 | 固定规则 |
|---|---|
| 预算 | 创建时冻结番茄数、每番茄分钟数、总预算；设置变化不改旧预算或当前轮 |
| 重算预算 | 明确用户动作；保存旧值、新值和原因；实际投入不变 |
| 时间 | 主钟控制一轮节奏；任务按片段独立累加；暂停和休息不增加 |
| 换任务 | 当前轮不重置；A 封口、B 开段；暂停换任务不恢复计时 |
| 达预计 | 进度封顶 100%，超时单列；不会自动完成任务 |
| 完成任务 | 显式完成；不补预算，不赠完整轮数；完成当前任务时主钟暂停且保留剩余 |
| 归档 | `archivedAt` 与完成状态分离；恢复归档不取消已完成 |
| 后台 | Rust 独立计时和结算，本版落地；v1.3 只复用，不再重写 |
| 档案 | 本地稳定 UUID 游客档案；所有读写已有真实档案边界，即使本版仅激活一个档案 |

### 2. 数据模型约束

下表为逻辑契约，字段名可适配现有 snake_case/camelCase。UUID 沿用仓库已有 v4 功能即可，不因排序目的强制换 UUIDv7。

| 对象 | 最小数据 | 关键约束 |
|---|---|---|
| profiles | id、kind、createdAt；accountSubject 预留可空 | 游客 ID 每次安装首次生成并持久化，不在所有机器固定为 `local` |
| categories | id、profileId、name、normalizedName、sortOrder、archivedAt | 名称非空；同档案同名可提示/拒绝，但不能跨账号共用一行 |
| projects | id、profileId、categoryId、name、description、plannedStartDate、dueDate、completedAt、archivedAt、sortOrder | 类别必须同档案；不强制同档案所有项目名称全局唯一；同名不同项目以 ID 区分 |
| tasks | 原稳定 id；profileId、projectId?、title、priority、status、archivedAt、dueDate、notes、sortOrder、预算快照 | status=`todo/doing/done/canceled`，归档单独存；旧 done 由状态投影，不双写两套权威状态 |
| task_budget_history | id、profileId、taskId、before/after 预算、source、createdAt | 创建/迁移/主动修改都有来源；写任务预算与历史同事务 |
| sessions | id、profileId、originDeviceId、plannedMs、roundState、finishReason、completedFullRound、历史快照、资格摘要 | 从开始就能持久追踪活动轮次；旧记录可保留 legacyStatus；资格摘要由片段推导 |
| focus_segments | id、profileId、sessionId、taskId?、项目/类别 ID 与名称快照、任务标题快照、开始/结束时间、effectiveMs、lifecycle、contributionState、temporalPrecision、source | lifecycle=`open/closed`；contributionState=`provisional/confirmed/void`；单位全为毫秒 |
| timer_runtime | profileId、deviceId、sessionId、boundTaskId、remainingMs、state、revision、checkpoint、恢复信息 | 设备上至多一个活动运行上下文；每个快照可追溯档案与轮次 |
| command_receipts | profileId、operationId、command、payloadHash、phase、result | 重试查回执；相同操作 ID 不同参数拒绝；不与未来网络 outbox 混为一物 |
| migration_audit | migrationId、sourceFingerprint、映射、预算基准、精度标记、状态 | 预览确认与实际输入一致；重复执行不重复创建 |
| profile_settings / device_settings | 个人偏好按档案；窗口坐标、显示器、deviceId、本机资源路径单独保存 | 不沿用全局 `settings.id=1` 读取其他账号偏好；窗口位置不混入业务备份 |

业务实体以 `(profile_id,id)` 作为作用域主键，ID生成仍采用全局随机UUID；允许同一来源对象在隔离恢复档案中保留原ID。关系保护使用复合外键并在命令层校验。`project(profileId,categoryId)`、`task(profileId,projectId)`、`segment(profileId,sessionId/taskId)` 都不得跨档案。历史快照不得 `ON DELETE CASCADE`。历史对象消失时可保留快照 ID 与名称，不要求删除历史记录来满足外键。迁入同一目标档案发生同ID不同内容时再按迁入协议重映射。

为同设备活动片段建立唯一性约束；所有更改当前任务归属的操作由同一计时协调器执行。不能只靠 UI 禁用防止两个窗口/托盘同时写入。

### 3. 迁移：先预览，再提交

**当前实际 DB schema=3，备份格式=2。** 本版第一次新迁移使用下一号 4；本版若确有追加迁移则继续递增，不把整个未来路线写死在 Schema v4。已经发布的迁移脚本不可改写语义。

#### MIG-12 迁移协议

1. 首次打开旧库先进入只读检查/迁移准备模式，不启动计时写入。

#### 明确的旧数据映射

- 默认类别可创建“学习、工作、生活、其他”。旧任务标签可提供类别建议，但一个旧项目关联多个标签时，显示冲突让用户为项目选择类别；不拆成多个同名项目，也不偷偷跟随每个任务标签。
- 项目名只按 trim 后完全相同聚合为迁移候选，不大小写模糊归并、不近似合并。仅此迁移候选归并，不推导今后项目全局唯一。
- 旧默认“通用”默认建议映为**独立任务**，预览可改为一个正式项目；明确展示最终选择，不自动制造用户从未创建的正式项目。
- 预算建议使用迁移时设置，但必须由用户确认基准。保存 `budgetSource=migration_estimate`、基准分钟数、原番茄数；不能标为创建时准确预算。异常值单列处理，不静默归零。
- 历史归属只从 `session.project_snapshot` 等发生时字段映射；任务当前已经在 B，不代表此前会话属于 B。映射不唯一就保留 `legacy_unmapped` 与原名称。
- 每个旧会话生成稳定、可重试的历史贡献记录，例如由旧 session ID 推导迁移记录 ID；不能每次迁移生成新的随机 ID。保留所有旧会话，合格贡献用 `focused_seconds × 1000`。
- 旧记录没有暂停区间：保存 `temporalPrecision=legacy_total_only`，保留原 startedAt/endedAt 作为元数据，**不得伪装成连续有效片段**。旧总量按原开始日归属；不对该范围做精确跨午夜分摊或多设备区间并集。
- 旧运行轮没有可靠检查点：显示可证明的已存状态和未知区间。保持暂停，提供放弃不确定尾段/由用户核对保存的入口；任何人工调整有来源，不自动从墙钟补满整轮。迁移完成前必须处理该旧活动轮。

### 4. 时间账本的可执行契约

#### 4.1 精度、资格和确认

Rust 使用注入式 Clock，运行时经过时间基于单调时钟；UTC 时间用于发生位置和持久化。新片段只覆盖实际运行，暂停、休息、休眠各有边界。保留毫秒余量，不能每次暂停先取整为秒。

对于任务 T：

```text
confirmedMs(T) = T 的 confirmed 片段有效毫秒之和
provisionalMs(T) = 当前未结束轮次中 T 的全部 provisional 有效毫秒
                  （含已封口片段与当前活动片段；同一片段只出现一次）
displayedMs(T) = confirmedMs(T) + provisionalMs(T)
progress(T) = min(1, displayedMs(T) / targetMs(T))
overtimeMs(T) = max(0, displayedMs(T) - targetMs(T))
```

预算必须为正且经 Rust 上限校验。未指定任务的片段计入个人账本，不分配给某个任务。实时暂计与已保存投入在 UI 中可分辨。

30 秒规则按**同一轮次保留的有效时长**判断，包含不同任务片段，排除 void。保存边界重新检查 `retainedEffectiveMs >= 30000`，达到后按稳定片段 ID 确认该会话待确认的已保存部分；不对每个片段另设 30 秒门槛。

为避免“保存”含义混乱，固定如下：

| 事件 | 持久化 | 贡献状态 |
|---|---|---|
| 周期检查点 | 更新当前 provisional 片段的可恢复长度 | 不自动变成完整轮数，不因 tick 发奖 |
| 暂停/切任务 | 封口并保存 provisional 片段 | 本版不因普通暂停/切换自动确认贡献；实时进度仍包含它们 |
| 完成当前任务并保存 | 冻结当前轮，保存片段及任务完成态 | 会话达门槛则确认已保留片段；不足门槛则保留 provisional，任务仍可完成 |
| 结束并保存/重启前保存/自然到期 | 封口当前片段，最终判断资格 | 达门槛确认；最终不足门槛的 provisional 转 void |
| 放弃本轮未保存部分 | 结束轮次，保留已确认片段 | 只将尚未确认部分转 void；不撤回此前明确保存的贡献 |

一个会话可能“已保存 A，后来放弃 B”。其 A 贡献继续可见；不能因为最终 finishReason=abandoned 把 A 从统计中抹去。完整番茄仅在自然达到本轮计划有效时长且没有被放弃的缺口时计 1；手动 30 秒不计完整番茄。

必须覆盖：A 20 秒完成并保存 → A 完成但时间暂不入统计 → 同一轮 B 再 15 秒后结束保存 → A=20 秒、B=15 秒、合计35秒、完整轮数0。若 A 20秒后直接结束，则 A 仍完成，时间不计入有效统计。

#### 4.2 主钟与任务操作

| 操作 | 状态变化与事务边界 |
|---|---|
| start | 创建 session、首个片段和运行状态；冻结本轮计划，不修改任务预算 |
| pause | 封口当前片段，保存 remainingMs，状态 paused |
| resume | 只从 paused 接续剩余，按当前绑定开新片段；不恢复已完成/归档任务绑定 |
| switch task | running 时同事务封口 A、绑定 B、打开 B；remainingMs 仅扣实际经过量；paused 时仅换绑定、不产生运行片段 |
| move active task to project | 在同一协调锁/事务内封口旧归属，再改当前项目，若原来运行则以新快照继续；主钟不重置 |
| rename project/category | 既有片段快照保持；当前已开的片段也不追写；后续新片段取新名，汇总仍为同一稳定 ID |
| finish | 保存有资格的贡献后结束本轮；不等于任务完成，不自动休息 |
| restart | 原子结束并保存旧轮+建立新轮；新轮用当前设置；操作回执避免重试再开一轮 |
| abandon | UI 明示仅放弃尚未确认的部分；已确认贡献不变；旧 reset 的放弃语义不能冒充 restart |
| archive current task/project | 先冻结当前轮再保存归档/解绑；错误后保持暂停；历史不变 |

普通任务详情“标记完成”与“完成当前任务并保存”分开：未绑定任务可单独更改状态，不触碰其他任务的主钟；被当前轮绑定的任务必须走完整保存操作。

#### 4.3 `complete_task_now` 的失败语义

请求：`operationId + activeSessionId + taskId + expectedTimerRevision + expectedTaskRevision`，档案来自 Rust 上下文。

1. 先查相同操作回执；否则在计时协调锁中校验对象和版本。旧窗口点到已换绑的任务返回 CONFLICT，不暂停/完成另一个任务。
2. 校验成功后在后台捕获冻结时刻 t0，使主钟停止累积。该**暂停保护**与下面的业务原子提交分开定义。
3. 最小持久准备记录写入 paused、remainingMs、封口的 provisional 尾段及操作 phase。业务事务再做：资格确认/贡献保存 + 任务完成 + 解绑 + 成功回执。贡献确认和任务完成必须一起成功或一起失败。
4. 业务提交失败：保持已经暂停的轮次，任务未完成、贡献未误确认，保留 operationId 重试。准备中的操作只允许重试或显式取消；其他变更先返回可解释冲突，不能完成错对象。
5. 连“暂停准备记录”都写不进去（磁盘满等）：Rust 内存进入 paused/error，禁止继续运行，不宣布保存成功；进程重开仅恢复最后一个已持久检查点并报告未知尾段。无法保证失败介质上的 t0 也落盘，不编造零损失承诺。
6. 撤销完成使用 completionOperationId 和任务最新 revision；仅恢复任务状态，保留真实片段，主钟仍暂停、不会自动重新绑定。若任务已被后续修改，要求刷新后普通编辑，不能撤掉别人的新状态。

到期竞争由同一个协调器定序：服务接收命令时已经到期则先自然结算，该“当前任务完成”请求返回已结算冲突并刷新；用户仍可在详情完成该任务。到期前取得锁的请求先冻结，阻止之后 ticker 重复结算。**不保证两个互斥动作都成功，只保证结果完整且时间仅计一次。**

#### 4.4 后台、恢复和通知

- 从 repository 抽出唯一计时协调入口（可命名 TimerService），保留 SQL 访问边界。`lib.rs:ticker`、commands、托盘和快捷键最终都调用它。
- ticker 到期直接提交结算，不只发 `timer-expired`。未落库成功不标记“已结算”；DB 忙退避重试，到期后不继续累加超过计划的时间。
- session 终态、片段确认、timer 状态和自动休息决策在后端同事务或受回执保护的恢复协议中完成。自动休息只由新自然专注完成触发一次。
- 当前 `autoStartBreak` 行为保留；禁止主窗/小窗各收到广播就 start。音效/通知以后台单一调度者处理，UI 广播只刷新；外部音效无法与 SQLite 原子提交，异常恢复默认不补播，承诺正常竞争不重复，不承诺跨崩溃绝对恰好一次。
- 心跳检查点暂定每1秒及所有命令边界保存；实际 I/O 延迟纳入恢复报告，不能把1秒写成无条件最大损失保证。数据库繁忙不能让前端继续宣称已保存。
- 默认休眠暂停；使用 Windows 电源事件及明确的单调计时实现并实测。大间隔不等于用户没专注，不能简单“超过N秒就把整段抹掉”；事件缺失时保留可信检查点、标记不确定范围并暂停等待核对。
- 锁屏是否继续作为本机设置；进程崩溃/异常退出重开一律暂停，报告已恢复量与未知尾段，不根据 UTC 截止时间自动补齐离开时间。
- 系统时间跳变封口或标记 `clock_anomaly`，保留单调测得有效量及时间质量；不能制造负时长，也不把异常区间当成可精确并集的时间段。
- `timer.rs` 在确认全仓引用、模块注册及测试用途后删除/归档旧实现，不能把旧代码启用成为第二套计时引擎。

### 5. 类别、项目、任务和统计

- 类别支持新建、改名、排序、归档/恢复；删除前移动全部项目。归档类别含活动任务时先暂停；不把隐藏类别用于新项目默认值。
- 项目创建只需名称和类别；说明、计划开始日、截止日在更多选项。日期为日历日期，不用 UTC 午夜代替用户日期。任务截止晚于项目截止时提示，不替用户修改。
- 项目完成率=当前归属且未取消任务的完成数/任务数。归档不改变任务是否完成，也不自动移出分母；从计划移除用取消/转移等明确动作。0项显示“尚未添加任务”。全部完成只提示用户完成项目，不自动完成；存在未完成任务时拒绝静默完成项目。
- 项目解除/删除先预览：可归档，或解除任务归属后软删除；历史项目投入保留。恢复归档不会复活已完成任务。
- 任务快速创建：标题、项目、预计番茄数及分钟换算；优先级/日期/备注在更多选项。项目选择按类别分组、可搜索、最近使用与就地新建。项目详情内创建默认绑定当前项目。
- 详情可编辑元信息、预算、状态；复制任务仅复制计划字段，生成新 ID，累计时长从0开始。草稿/筛选/滚动位置跨页保留，以档案隔离。
- 搜索标题和项目；类别/项目/状态/归档/截止范围组合筛选；排序最近更新/优先级/截止/手动。分页有稳定 ID 兜底与上限，关键词转义、参数化 SQL；前端不一次加载全部历史。
- 单任务自身时长从其历史片段累计；项目历史从 `projectIdSnapshot` 累计，项目当前完成率从当前关系计算。移动后 A历史40、B历史20、任务总60；改名后仍是一个项目。
- 新有效区间按日历边界求交，暂停间隙不摊入。查询总量只从片段/历史贡献规范集合求和，**不可同时把 sessions 总秒数和迁移片段再加一次**。跨午夜完整轮数归自然完成时刻，时间按区间；旧历史轮数口径在迁移报告中说明。
- 现有dailyGoal继续按“合格专注会话数”解释并明确标注，按会话开始日及稳定sessionId计数；新增“完整番茄轮数”独立展示。中途保存和最终结算不能让同一会话贡献两次次数；两类次数不混用，时间的分日求和与轮次数的日期归属分别定义。

### 6. 字体与可读性

正文提供系统默认与 Noto Sans SC 选项，数字保留既有 Inter/DM Mono 与等宽数字。优先用离线打包的适当子集配系统回退，或可离线安装的本地字体资源包；生僻字、英文与数字混排均需验收。不能仅因体积大就删除 Noto 选项。

新增字体偏好标识、紧凑/舒适密度、文字大小和独立背景亮度控制，动态效果继续复用/完善 reduceMotion；新设置与 fontFamily 一起声明 DTO、默认值、持久化和备份行为。个人偏好标识将可同步，实际字体文件路径只在本机解析。

设置归属固定：专注/休息时长、dailyGoal、自动轮次偏好、字体标识、文字大小、密度、背景亮度和用户reduceMotion偏好属于profile设置；声音/系统通知开关、锁屏行为、开机启动、快捷键、窗口坐标和本机字体文件路径属于device设置。系统的降低动态偏好可在本机覆盖呈现，但不反向改写云端用户偏好。迁移原settings时明确拆分，备份只带profile设置。

正文建议14–16px、辅助12–13px、主计时56–72px；统一 CSS token，操作目标至少36–40px；中文长标题两行截断并可在详情完整阅读。焦点、错误、选中同时有形状/文字，不只靠颜色或透明度。

本次上传没有字体/鱼素材包。执行时先核查仓库/用户提供的资源，缺失则从可核验来源获取，保留许可、版本、来源及哈希并登记 THIRD_PARTY_NOTICES；不能把原路线的“已下载”当成当前仓库已具备文件。

| 80分钟预算实际60完成 | 完成且实际60，不补成80 |

| 保存事务故障/断电/到期竞争 | 状态符合 §4.3，重试不重复，不宣称未落盘时间已保存 |
| 跨午夜运行且中途暂停 | 有效时间按实际区间分日；合计守恒 |
| 移项目/类别/改名/归档恢复 | 当前组织改变，历史快照不改，完成状态不被归档覆盖 |
| 同档案/跨档案非法外键 | 后端和DB拒绝，不只依赖前端 |
| 10万会话、5000任务 | 分页；计时写锁不被统计长期占用；记录基线硬件、p50/p95、最大阻塞和内存 |
| 迁移副本失败/取消/重复、备份往返 | 保原数据、无重复、总量一致；新数据可立即恢复 |

性能目标初设：参考 Windows 设备热缓存任务查询 p95≤200ms、常用月统计 p95≤500ms；P120-01 记录设备后冻结指标。达不到时优先索引/分页/聚合优化，不通过删数据或减少统计范围“达标”。冷启动和迁移耗时单列，不混入热查询指标。

长休每N轮、自动下一轮开关、可编辑25/5、40/10、50/10预设和预计结束时间可在主链路验收后独立补充。只有明确实施并验收的可选项才写入本版已交付清单。

# PLAN-140

## v1.4.0 可选账号与云备份计划

> 前置：v1.2 档案隔离和完整新格式备份已经可用，正常顺序在v1.3后发布。
> 建议分支：`feature/v1.4-account-backup`。状态：待实施。通用规则见 [索引](#plan-index)。
> 本版是版本化云备份，不提供多设备自动合并；双向同步单独在v1.5实现。

### 1. 固定范围与外部门

离线核心功能不要求账号。首次可用邮箱验证码登录；游客档案、账号本地缓存分开；云端备份版本可上传、列出、下载、删除和预览恢复；提供个人数据导出与清除云备份。设置页不放不可用的“设备管理即将支持”按钮冒充功能。

服务端厂商本轮不凭空锁定。可以先实现 AuthService/BackupService 接口、测试适配器和本地档案逻辑；真实部署前形成一份简短决策记录：目标用户地区实测连通性、验证码投递、数据区域、存储/流量/邮件预算、运营责任、服务能力。候选可包含托管Auth+数据库+对象存储或自建API，但不把某厂商可达性当作已知事实。

**厂商选择是v1.4真实认证/云备份联调的前置门，不是整条路线的前置门。** 未完成服务端与真实往返测试只能说“本地子阶段完成”，不能把只做了本地档案的版本标为“登录与云备份已交付”。使用用户资源、付费部署和生产发布依据当次授权执行。

### 2. 本地身份与切换

- Rust 持有 `ActiveContext(profileId, contextGeneration)`；UI不能任意传profileId取得其他账号数据。所有CRUD、统计、导出、恢复、缓存、草稿和计时操作从该上下文取归属。
- 账号以认证服务的稳定 subject 绑定本地profile；**不以可变邮箱作为主键**。profile本地ID与服务器userId不强行等同。
- settings、timer_runtime、迁移审计、后台任务也在隔离范围内，不能只清空 tasks/logs。
- 同机A→B：先冻结并保存A当前轮次 → 停止/作废A网络工作 → 递增contextGeneration → 清理两窗内存/草稿/缓存 → bootstrap B。若A暂停保存失败，不切到B伪装成功。
- 网络工作捕获启动时的profile、subject和generation。旧A响应到达后只能处理A自己的工作结果，不能把它写到B页面或换用B凭据继续请求。退出不能只替换全局token字符串。
- 离线/登录过期时，当前账号的已解锁本地档案继续可用；显式退出则清除凭据和UI会话，回到游客档案，游客不自动显示账号缓存。重新访问已退出的账号档案需重新认证；不因此删除旧缓存。
- 本地隔离不等于磁盘加密；如实说明同一Windows用户可直接访问应用文件，不用登录按钮承诺抵御本机文件读取。

### 3. 首次登录与游客迁移

登录只建立身份，不自动下载/恢复最新云备份，更不自动把游客数据上传。

向用户展示：本机游客任务/项目/会话/贡献数量、目标账号本地缓存数量、云备份版本概况。提供“迁入此账号”或“保留游客档案，打开账号档案”。没有本地账号缓存时打开空账号档案，可另外选择恢复云备份。

迁入流程：

1. 暂停并保存游客活动轮次，备份游客与被影响账号的本地数据。
2. 建立 `migrationId + sourceProfile + targetSubject + sourceFingerprint`；预览新增/相同ID相同内容/相同ID不同内容的数量。
3. 同ID相同内容去重；同ID不同内容必须预览并选择保留目标或作为独立副本导入。作为副本时给对象及相关外键统一重映射，留下来源映射，不能只改task ID漏改session/segment。
4. 一个事务内修改归属/插入合并结果和迁移回执，校验关系仍同档案。失败不半迁移；重试同migrationId不重复导入。
5. “迁入”成功后源数据从游客活动视图移出，原游客档案和恢复备份仍可追溯，不让两个活动档案看似各有一份待重复迁入的数据。
6. 原轮次保存为原始来源和暂停状态；新账号不自动开始计时。是否立即上传由用户另行操作。

### 4. 认证与凭据

认证接口放Rust，建议 `AuthService.requestCode/verifyCode/refresh/logout`；验证码长度、有效期及重发策略以选定服务端能力为准，客户端不伪造固定“6位10分钟”保证。必须有服务端单次使用、过期、重发/尝试限流；用错误/过期/限流/超时状态驱动UI。

token写Windows系统凭据存储，不落SQLite、localStorage、日志或导出。凭据键包含应用标识和账号/档案映射；token不返回前端。CI可注入内存测试适配器，生产构建不能在系统凭据不可用时静默降级明文或内存“假持久化”。

使用邮箱验证码输入不要求浏览器OAuth回跳；若所选服务使用magic link或后续OAuth，另补回跳注册和state/nonce验证，不能把两种流程混写。

退出先使本地会话失效并清理凭据；联网时请求远端撤销。离线时不宣称已远端撤销，说明远端状态待下次可验证；本机依然立即退出。并发刷新token串行化，账号切换后旧刷新不得写回新上下文。

### 5. 云备份格式与边界

命名使用 **BackupService**，不要把整包备份接口称为增量SyncEngine。

| 元数据 | 规则 |
|---|---|
| formatVersion | 独立于SQLite schema，明确支持的读取/升级版本；未来版本拒绝 |
| backupId / operationId | 上传重试稳定ID；同ID同hash返回同备份，同ID不同hash拒绝 |
| appVersion / exportedAt | 描述生成环境和时间，不作为授权依据 |
| 内容清单/计数/hash/压缩后大小 | 用于完整性、配额与预览；流式计算，限制解压大小和条目数 |
| 账号归属 | 服务器从认证身份确定；不信任文件内的profileId/userId |
| 业务内容 | 当前档案全部类别、项目、任务、预算历史、会话、片段、迁移精度和个人偏好；包含未合格/放弃/休息记录 |
| 不包括 | token、凭据、其他档案、窗口坐标、本机资源路径、同步游标/发送队列；历史originDeviceId仅作来源保留 |

备份生成采用数据库一致性快照，不逐表跨多个不一致时刻读取。若用户要求包含当前进行中轮次，在后端捕获一个可恢复检查点并在备份中规范为暂停状态，导出之后本机可以继续；云恢复绝不自动运行备份中的计时器。

构建不可变备份快照后释放DB写协调锁，再执行压缩、上传和网络重试。上传/下载不阻塞本地计时，**应用恢复时会短暂停写**，不能一面覆盖档案一面允许计时写旧对象。

服务端建议将元数据与受保护对象存储分离；无论实际选择如何，都要限制单份大小、用户总配额、保留版本数和下载授权。先完成对象校验再将备份标为ready，上传中断不能出现“列表可恢复但文件不完整”。服务端时间用于版本列表稳定排序并以backupId兜底。

### 6. 恢复协议

“恢复”是**替换当前账号档案的业务快照**，不是合并多个设备。预览必须明确这一点，并列本机新增但备份中没有的数据。手动文件导入也使用相同语义；想要合并需走明确的迁入/导入模式，不能把两个动作共用含糊按钮。

1. 下载到临时文件，先校验归属、格式、hash、大小和内部关系；未来格式或非法引用拒绝。不能把JSON中的profileId直接用于SQL目标。
2. 在临时数据库/隔离暂存模型中解析迁移并生成预览，显示会被新增、替换、移除的对象数量和活动轮次处理方式。
3. 用户确认后冻结当前轮，创建并验证恢复前备份；成功之前不修改目标档案。
4. 进入当前档案维护状态，在短事务内替换该profile的业务数据并写 `restoreOperationId + backupId/hash + expectedProfileRevision` 回执，其他profile不受影响。恢复timer为paused/idle，deviceId和本机凭据不从备份覆盖。
5. 验证外键、资格和聚合对账后提交；失败回滚目标事务，保留原档案和恢复前备份。提交后清空两窗缓存并bootstrap。
6. 重试相同恢复操作返回同回执。用户随后做了新修改，再次选择同一备份是**新的替换操作**，必须重新预览，不能因“这个backupId以前恢复过”就返回虚假成功。

当前基线 `repository.rs:import_data` 会整库DELETE，调用者也没有自动恢复前备份。本版只能复用解析等经过验证的部件，不能直接沿用原函数破坏其他档案。

### 7. 服务端授权、数据控制与文案

所有上传/列表/下载/删除由认证subject约束。对象路径、备份ID、客户端profileId均不是授权凭据；测试A拿到B备份ID也不能读取/覆盖/删除。客户端不包含管理员密钥。

状态文案使用“已保存在本机”“正在备份”“已备份至…（该快照时间）”“本机有更新，尚未备份”“上传失败，可重试”；过期写“重新登录后继续备份”。不能在v1.4显示“已同步”暗示自动合并。

说明实际处理的数据：认证邮箱以及用户选择上传的任务、备注、日期、会话、片段、偏好和设备来源信息。不能写“仅收集邮箱”。提供个人导出、删除单个备份、清除云备份的明确确认；清除云备份不删除本机数据，也不伪装为已删除认证账号。若提供注销账号，必须完成认证身份和业务数据的对应删除流程。

# PLAN-150

## v1.5.0 多设备增量同步与冲突处理计划

> 前置：v1.4真实认证、账号隔离、备份恢复已经验收；基于前版实际代码细化API。
> 建议分支：`feature/v1.5-sync`。状态：待实施。通用约束见 [索引](#plan-index)。
> 本版没有植树/奖励，没有跨设备接力控制运行钟，没有在线权威计时或排行榜。

### 1. 同步边界

同步已持久业务实体和**已封口的不可变片段**、片段确认/撤销等状态事件。当前open片段、运行时单调时钟锚点、窗口坐标、本机凭据和设备资源路径不同步。封口后尚未达资格的片段可同步为 provisional，后续由同一来源设备的资格事件确认，接收设备不重跑本地30秒猜测。

任务、预算、类别、项目和个人偏好可以离线修改；本地事务成功即显示“已保存在本机”，网络失败不回滚专注结果。个人偏好同步字段包括默认时长、字体偏好标识、文字/主题等；窗口位置和字体文件路径仅本地，缺少字体时本机回退。声音等明确本机环境选项由设置白名单排除，不自动把整份device_settings推上云。

活动钟只在来源设备运行。另一设备的只读状态使用独立的网络presence接口（设备、任务概要、状态、lastSeen、过期时间），不能把Tauri本机 `timer-changed` 广播当跨设备协议。presence离线失效后显示“上次活动”，不假装知道对方仍在计时；不允许远程暂停/接力。

### 2. 协议必须解决的四个问题

#### 2.1 本地提交和出站事件不能分离

每次业务变更与相应outbox事务组同一SQLite事务。原子完成任务可产生片段封口、资格确认、任务完成和轮次状态等多个事件，但它们属于一个transactionGroup。重试命令返回既有回执，不新增另一组事件。

已封口片段的基础事实不可覆盖；后续确认、作废或人工纠错生成引用该片段的事件。不得每秒上传可变open片段，也不得将“保存累计总时长”作为独立可相加的同步对象。

#### 2.2 幂等、因果与字段冲突各用正确的信息

一个本地自增 `rev` 或Lamport数字不能判断两个设备是否并发。最小协议如下：

| 字段 | 用途 |
|---|---|
| protocolVersion | 消息格式及合并规则版本，独立于DB/备份版本 |
| accountEpoch | 云端数据代际，防止清空云数据后旧队列重新灌回 |
| transactionId / eventId | 事务组和事件的稳定幂等ID |
| deviceId / deviceSeq | 已注册来源设备及单调持久的设备序列；不能用本地时间替代 |
| entityType / entityId / op | 明确变更对象及create/patch/delete/restore/correct等动作 |
| changedFields / values | 仅包含本次修改字段，不整对象覆盖未修改字段 |
| baseFieldVersions | 每个被改字段对应的基础版本token，用于检测并发 |
| dependsOn | 引用先前离线事件/创建事务，建立本设备队列因果依赖 |
| payloadHash | 相同ID不同内容拒绝，防止幂等键被错误复用 |

字段版本token采用最近写该字段的稳定eventId（初始值引用seed事件）。离线连续两次修改时，第二次的baseFieldVersion可以引用第一次尚未ACK的eventId；依赖满足后才发送/处理第二次。服务端ACK不得重新生成该eventId。Lamport可作为辅助排序信息，但不是冲突判定依据。

- 基础版本仍等于服务端该字段版本：可以应用。
- 修改不同字段：各自基础版本匹配则可合并。
- 同字段基础版本落后：创建持久冲突，保存现值/候选值/基础版本/相关事件。先到达的值不是“自动胜出且丢弃另一方”，UI标注冲突未解决。
- 解决冲突是新事件，引用双方版本及conflictId；若又有新修改，解决请求需要重新核对，不能覆盖新值。
- 预算数值和预算快照/历史作为同一业务单元更新；项目categoryId和归属相关字段也需关系校验，不能把相关字段任意拆开“合并成功”。

#### 2.3 服务端顺序必须是提交顺序

`server_received_at`不能单独作游标：同毫秒可有多个事件，客户端时钟不可比较，未提交的低序号也可能晚到。

服务端为每个账号数据代际建立提交有序的 `serverSeq`。推荐在事务内锁定该账号的序号行，分配序号、写整个事务组、更新状态并提交后释放；保证不会先向客户端暴露高序号，之后又补提交一个更低序号。**不能仅给表加自增ID，就宣称已经得到安全提交游标。**

拉取游标至少包含 `accountEpoch + lastCommittedServerSeq`，按该序列分页；事务组不跨不可识别的半包边界。也可使用等价不透明游标，但必须证明同样的无漏读性质。

#### 2.4 服务端要验证业务，不能只是保存任意JSON

服务端从认证身份及已注册设备确定归属；验证protocol、epoch、payload结构/范围、稳定ID、事务组完整性、同用户外键、字段基础版本和墓碑规则。

服务端对一个事务组：全部ACK、全部duplicate、全部conflict/validation failure，不把“任务完成”应用成功但把相应时间片段漏掉。只要客户端提供同一组ID和内容，重试返回既有结果。独立事务组可继续，依赖失败的组保持blocked。

### 3. 本地存储与同步引擎

| 对象 | 最小字段/约束 |
|---|---|
| sync_outbox | profileId、accountEpoch、transactionId、eventId、payload、payloadHash、deviceSeq、dependsOn、state、attempts、nextAttemptAt；状态pending/inflight/acked/blocked |
| sync_cursor | profileId、服务端账号映射、accountEpoch、stream、lastServerSeq；不能只按entity存一个全局游标 |
| sync_inbox | profileId、epoch、eventId唯一，关联serverSeq/transactionId；应用去重 |
| entity_field_versions | entityType/entityId/field/versionToken；保存真正基础版本 |
| sync_conflicts | conflictId、双方版本和值、类型、状态、解决事件 |
| tombstones | entityId、删除事件/版本、服务端顺序、epoch、恢复关系 |
| sync_initialization | profileId、snapshotRevision、bootstrapId、阶段、seed完成位置 |

schema使用上一版之后的下一号，不写死“v4→v5”。同步支持的数据表都有明确序列化版本、导出和恢复规则。

#### 同步循环

1. 取得固定的账号/档案/epoch上下文，检查认证状态；网络可达性以实际请求结果判断，不能只看操作系统“在线”。
2. 按依赖关系push待发事务组。批量需同时限制条目数和字节数，限额由服务端契约规定；重试保留全部ID。
3. 分组处理ACK/duplicate/conflict/validation failure；只把明确确认的组标记acked。请求丢响应不视为失败回滚业务，稍后重试查同一组。
4. pull收到的完整事务组在一个本地事务中执行：inbox去重 → 校验/保存冲突 → 应用远端投影 → 更新字段版本 → 推进cursor。
5. 远端应用路径必须带 `origin=remote`，不再次生成出站事件；用户解决冲突/人工修正才新增本地事件。
6. 执行期间断电：业务+outbox仍同生共死；inflight重启后可重试；远端应用与cursor一起回滚或一起提交，不能跳过未应用事务。
7. 暂时网络错误指数退避加抖动；401暂停等待重新认证；epoch错误阻断旧队列；永久校验错误进入可见blocked，不能无限快速重试。
8. 换号时取消/隔离旧worker；所有回调验证捕获上下文，不能拿B凭据发送A队列。网络等待和大批计算不持有计时DB锁。

坏事件/未知protocol：保留原始响应到受限诊断、停止推进该游标并提示更新/修复。**不能“跳过损坏事件并继续游标”**，否则可能永久漏掉父对象或时间贡献。只有服务端给出经验证的新快照/纠正流程才能恢复，不靠客户端静默丢弃。

### 4. 首次同步、恢复与快照

#### 4.1 老设备首次启用

仅给未来写操作增加outbox会漏掉所有既有历史。必须捕获当前profile的一致性基线快照（包括归档、取消、隐藏会话、片段、预算历史和迁移元数据），生成稳定seed事件并记录初始化进度。

启用变更捕获与记录snapshotRevision在同一初始化屏障中完成；屏障后本地新增修改进入delta队列，不能落在“快照已读完但hook尚未开启”的空隙。可分批生成/传输seed，但seed/delta有依赖与可恢复位置；重复初始化不重复导入历史。

云端已存在数据时，先取云端快照/版本，再根据稳定ID和内容区分重复、独立对象与冲突，不盲目全量覆盖。名字相同的任务/项目不是同一个对象。

#### 4.2 新设备首次接入

下载账号快照与明确cutSeq，再从 `>cutSeq` 拉增量。快照按事务一致点生成；首次构建采用暂存/受控读取方式，不能把缺了一半项目外键的状态开放为可编辑完整档案。

等待期间可继续使用独立游客档案；如果允许在账号档案中创建新数据，必须放入隔离的本地覆盖层并接入同一合并流程，不能默默覆盖。为简化首版，账号初始化期间只读显示进度，游客工作不受影响。

#### 4.3 同步开启后的备份恢复

备份不携带旧token/outbox/cursor。恢复旧快照后不能把陈旧数据当普通新修改全量上传，复活已删除项。

默认提供“查看/恢复到隔离的本地档案”，不自动绑定同步。若用户明确要替换云端账号数据，走单独的云重置流程：备份、epoch更新、设备重新初始化和完整确认。v1.4的“直接替换当前档案”在同步开启状态下必须被该流程替代。

#### 4.4 删除云端数据与事件保留

清空云端账号数据时，服务端递增accountEpoch并清理/隔离旧数据及备份，撤销旧同步会话或要求重新授权。旧设备上传旧epoch一律拒绝，其本地数据保留但不自动灌回。用户可明确选择作为新数据重新导入，不能默认执行。

首版不物理清理删除墓碑和仍有依赖的事件。若后续做压缩/归档，必须提供带墓碑的快照cutSeq和最小有效游标；落后设备收到CURSOR_EXPIRED后完整重建，禁止跳到最新游标假装同步完。发布前记录容量评估与最低保留规则，不能只有“按阈值归档”的一句话。

### 5. 删除、归档与恢复

归档只是显示状态字段，不是删除墓碑；已完成任务被归档后完成态保留。删除任务/项目/类别走既定关系处理：项目先解除/转移任务，类别先转移项目；操作作为事务组同步，历史快照不级联删除。

旧设备修改已删除对象时，服务端保留墓碑并产生“删除vs修改”冲突；不通过普通upsert复活。恢复删除需要显式restore事件引用墓碑版本，依赖父对象有效；删除后又有新删除/恢复时重新检查基础版本。

远端删除或完成正被本机计时绑定的任务时，由本机协调器在当前时刻暂停并封口本机实际片段，再应用远端状态并解绑；本机封口是新的本地事实，可进入outbox，不能让“远端应用不回声”规则误删这条真实贡献。不得将远端事件的时间倒填成本机暂停时间。

### 6. 多设备重叠与统计对账

**两个设备离线同时专注可以发生。** 同步保留所有原始记录，不擅自删除某台设备的数据。

固定区分两种数值，避免“个人总量按并集、各任务按原量”却又声称两者必须相等：

```text
原始有效投入 = 所有去重ID后的confirmed片段effectiveMs之和
             = 各任务原始投入之和 + 未指定任务原始投入
可精确判重时长 = 时间质量可靠的新片段有效区间的并集长度
重叠量 = 同一可靠片段集合的求和 - 并集长度
```

个人概览显示去重后的可判重时长，并明确另列历史未能判重的投入；任务/项目保留原始投入视图。选择“分配去重时长”视图时，冲突重叠部分先进入待分配桶，用户明确归属后用修正事件分配，任何时刻不能给A和B各分同一分钟。

- 同任务两设备重叠：原始记录都在；该任务去重视图按并集。
- 不同任务重叠：重叠待核对，不按设备优先级或最新时间自动抢归属。
- legacy_total_only/clock_anomaly等片段没有可靠区间：按稳定来源ID去重保留总量，单列“历史/时间位置不确定，无法精确判重”，不把整段startedAt～endedAt拿来求并集。未核对前不显示“全部历史已精确去重”。
- 客户端UTC时钟偏差也可能伪造重叠；保留时间质量、来源设备和诊断，偏差异常标记待核对，不重写原始有效量。
- 修正通过独立事件撤销/重新分配贡献，保存原记录与修正链；统计从规范投影可重建。
- 日/周统计对可靠区间先与日历范围求交再并集；暂停空档不参与。跨不同设备时区的查询使用同一明确统计时区，切换时区只改变分桶，不改原始时间。
- 完整番茄数仍是来源设备自然完成事件去重计数，名称注明“完整轮次（按记录）”，不把两轮重叠直接转换成额外的去重分钟或成长奖励。

例：A任务10:00～10:20、B任务10:10～10:30，原始投入40分钟，去重30分钟，重叠10分钟待核对；不能同时显示“两个任务各20”并宣称其和为去重总30。没有重叠的A10+B15依旧严格合计25。

### 7. 设备与状态UI

设备注册使用本机持久ID和用户可读名称；服务端将认证会话与设备绑定。列当前设备、最近活跃、撤销入口。撤销设备后服务端拒绝其后续读写/刷新，不能仅在列表上标记disabled而仍接受既有token；已同步历史保留。

presence使用有过期时间的低频心跳，标注“截至…”。设备离线、进程退出、换号时撤销/自然过期；不将其当权威运行事实，也不阻塞本地计时。

主窗/设置显示：“已保存在本机”“N项待同步”“正在同步”“已同步至…”“登录已过期”“有冲突待处理”。只有队列清空且pull追到服务端本次高水位才显示该次已同步；无法连接时不刷新成功时间。冲突页并列双方字段值、删除冲突和重叠片段，解决动作可审计。

#### 发布前必须验证的故障矩阵

| 场景 | 预期 |
|---|---|
| 本地业务落库前/后断电 | 业务与outbox一起回滚/保留，不出现有业务无事件 |
| 服务端提交成功但ACK丢失 | 重发返回duplicate/同ACK，事件与贡献不翻倍 |
| 同毫秒大量事件、事务乱序到达 | 提交序游标不漏；依赖未到则阻塞，不跳过 |
| pull应用中断 | 数据和cursor一起回滚；重试不重复 |
| 坏负载/未知协议 | 不越过游标；状态可诊断、可恢复 |
| A改标题、B改预算 | 不同字段可合并；预算历史一起保留 |
| A/B并发改标题 | 保留双方并可显式解决，晚回执不覆盖新改动 |
| A删任务，B离线改后上线 | 保留墓碑，显示删改冲突，不复活 |
| 同设备连续离线编辑同字段 | 依赖和base版本正确，不能误报自己两次编辑为并发 |
| 开启同步前有10万会话 | 既有历史纳入seed；期间新专注进入delta，无空洞 |
| A任务完成并保存后同轮继续B | 接收设备看到原子事务组，最终确认不重复记A |
| 远端完成/删除本机活动任务 | 本机协调暂停、封口真实新增片段、不悬空 |
| 两设备同段时间不同任务专注 | 原始40/去重30/重叠10等数值正确，归属待核对 |
| A同步中退出、B登录 | Aworker不能使用B凭据或刷新B视图，游标/队列完全隔离 |
| 移除设备、旧token继续请求 | 服务端拒绝，历史不删除，本地核心继续可用 |
| 清空云数据后旧设备重连 | epoch不符，旧队列不回灌；恢复须明确流程 |
| 同步开启后恢复旧备份 | 隔离恢复或显式云重置，不自动上传复活数据 |
| 服务端不可达24小时后恢复 | 本地计时不阻塞，队列可恢复，统计不翻倍 |

本版完成的必要条件是**真实双设备、真实服务端**的矩阵通过；mock/FakeGateway测试只能证明局部契约。不得用“首次重放、冲突、墓碑稍后再补”来宣布双向同步完成。
